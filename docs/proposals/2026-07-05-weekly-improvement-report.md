# Weekly Improvement Report

**Date:** 2026-07-05

**Status:** Exploratory only — not being built yet. This document is a record of a
`/grill-me` interview that scoped the feature; no code has been written.

## Feature Request

User wants a summarized report telling them what to improve for today's session, based
on what mistakes they've made or been making. The report is generated by feeding a
trading journal's freeform `comment` text (on `tradeEntries`) to an LLM and asking it to
extract the pressing points.

## Relationship to Prior Proposals

A `/grill-me` session the day before (`docs/proposals/2026-07-04-previous-session-report.md`)
scoped a *different* shape of essentially the same idea: a manual session picker where
the user selects one specific past session and gets a right/wrong/improve report for it,
plus a session-renaming change (`unique-names-generator`) to make sessions distinguishable
in that picker.

**This proposal supersedes that one.** Mid-interview, the user confirmed the report
should be a rolling window over recent days, not a picker over individual sessions. The
session-picker UI and the `unique-names-generator` renaming work are dropped, not built
alongside this feature.

The sibling doc `docs/proposals/2026-07-04-post-session-review-notification.md` (the
"mark session reviewed" + notification-preferences feature) is still relevant background:
it's what introduced the `userPreferences` table this proposal extends.

## Findings

- **No existing report/insight feature.** Confirmed again this session — only
  `packages/api/src/services/stats.ts` (`GET /stats`) computes any aggregate, and it's
  account-wide/all-time, not window-scoped or narrative.
- **`generateObject` precedent exists only in the unmerged `development` worktree**
  (`services/voice.ts`): `generateObject({ model: openai("gpt-5.4-mini"), schema: <zod>,
  system, prompt })`. Needs porting/adapting, not copying — that worktree's schema differs
  (setups/characteristics vs. this app's plain `comment` field).
- **Route/service conventions:** flat `routes/*.ts` + `services/*.ts` pairs wired in
  `src/index.ts`, `authMiddleware` sets `c.get("userId")` per request
  (`packages/api/src/middleware/auth.ts`), ownership always enforced via
  `innerJoin(sessions, ...).where(eq(sessions.userId, userId))`.
- **No cron/scheduling infra** (confirmed again) — rules out server-push delivery,
  consistent with both prior proposals. This report is pull-only, generated on request.
- **Mobile RPC pattern:** `hc<AppType>` client in `apps/mobile/src/lib/api.ts`,
  query hooks in `apps/mobile/src/hooks/queries/` (`use-stats.ts` is the simplest
  template), sessions list/detail screens under `apps/mobile/src/app/(tabs)/sessions/`.
- **`userPreferences`** (`packages/api/src/db/schema.ts:16-21`) currently holds only
  `notificationTime` (`NOT NULL`), created only when a user opts into notifications —
  this proposal needs to change that (see Decision 4).

## Decisions Reached (in interview order)

1. **Scope: rolling 7-day window**, not a single picked session. Aggregates across all
   sessions, not tied to one `sessionId`.

2. **Trigger: on-demand, but persisted/cached.** No cron. First request for a given day
   generates and stores the report; later requests for that same day are served from the
   cache.

3. **LLM input includes outcome context, not just comment text.** Each entry fed to the
   LLM carries `decision`, `result`, `direction`, `r` alongside `comment`, so the model can
   correlate self-described mistakes with actual trade outcomes.

4. **Entry filter for the LLM narrative:** only entries with a non-empty `comment` AND
   `result != "open"` (closed trades only). Open entries are excluded from the narrative
   even if commented — there's no resolved outcome yet to judge as a mistake or strength —
   but they still count toward the `openCount` stat (Decision 6).

5. **Output shape: `generateObject` + Zod, not `generateText`.** Two capped-at-5 arrays,
   not one — `improvements[]` and `strengths[]`, each item `{ pattern, description,
   action/whyItMatters }` (exact field names per the prompt in Decision 9). No top-level
   `overview`/summary field — the prompt explicitly forbids preamble.

6. **Deterministic stats block, computed in code, never trusted to the LLM** — mirrors
   the existing `computeDecision` pattern in `services/tradeEntries.ts`:
   - `historicRatio`: all-time win rate over all closed entries, **excluding** the last 7
     days — a "before this week" baseline, not diluted by the week itself. Requires new
     query logic; the existing `GET /stats` endpoint is all-time *inclusive* and isn't a
     direct fit.
   - `weekRatio`: win rate over **all** closed entries in the 7-day window, regardless of
     whether they have a comment (broader set than the narrative's input).
   - `openCount`: count of `result = "open"` entries in the window.

7. **Empty-data behavior:** if there are zero commented, closed entries in the window,
   skip the LLM call entirely. Return stats-only (`historicRatio`/`weekRatio`/
   `openCount`), no `improvements`/`strengths`.
   - *Considered and rejected mid-interview:* gating generation on a minimum count of
     reviewed sessions (e.g. 5) in the window. Retracted — the only rule is
     comments-present → call LLM, else stats-only.

8. **Output language: Portuguese**, matching the language the comments are actually
   written in.

9. **Exact prompt supplied by the user** — a "trading performance coach" persona,
   structured Portuguese output (`## Pontos de melhoria`, `## Pontos fortes`, max 5 each,
   pattern-name + 1-sentence description + 1-sentence action/why-it-matters), with rules
   requiring 2+ corroborating entries per pattern, prioritizing
   execution/timing/risk-management issues over reasoning issues for improvements, and
   strictly separating praise from criticism. This prompt should be adapted to
   `generateObject`'s structured-field style (Decision 5) rather than emitted as raw
   markdown text.

10. **Window boundary: last 7 days through yesterday, excluding today.** The report preps
    for today's session using the prior week's data — today's (still-unfolding) entries
    aren't part of the window.

11. **Day boundaries use the user's local device timezone**, not server/UTC time. This
    affects both the 7-day window's edges and the cache key (Decision 12).

12. **Timezone plumbing:** the mobile app auto-upserts its device IANA timezone (e.g.
    `America/Sao_Paulo`) into `userPreferences` on every app launch, for *all* users —
    not just those who've opted into notifications. This means:
    - `userPreferences.notificationTime` becomes **nullable** (rows now get created
      regardless of notification opt-in).
    - `userPreferences` gains a new required `timezone` column.

13. **Cache key: one report per `(userId, reportDate)`**, where `reportDate` is the
    user's local calendar day. Not a content-fingerprint/hash-based invalidation scheme.

14. **Report history is kept and browsable** — not just the latest report. Two separate
    screens: a list of past report dates, and a detail screen per date (not a single
    combined screen).

15. **Backfill allowed:** any past date can be generated on first open, even one never
    visited while it was "today." No permanent gaps from the app being closed for a few
    days — lazy generation applies retroactively, using that date's own historical
    7-day window.

16. **List scope:** the list only shows dates that have at least one commented entry in
    their window — skips empty stub days entirely. This is independent of whether that
    date's report has actually been generated/cached yet (Decision 15 covers that).

17. **Generation trigger is the detail screen, not the list.** Opening the list surfaces
    an entry per qualifying date (Decision 16); opening a specific date's *detail* screen
    is what lazily triggers generation if it isn't cached yet.

18. **Entry point: within the existing sessions list screen**, not a new tab and not the
    Home tab.

19. **Storage shape: JSONB columns**, not a normalized child table. `improvements` and
    `strengths` are read/written only as a whole alongside their parent report row, so
    there's no need to query/filter individual points independently.

## Suggested Implementation Sketch (for future reference only)

- **Schema (`packages/api/src/db/schema.ts`):**
  - New `dailyReports` table: `id`, `userId`, `reportDate` (date), `historicRatio`,
    `weekRatio`, `openCount`, `improvements` (jsonb), `strengths` (jsonb), `createdAt`.
    Unique on `(userId, reportDate)`.
  - `userPreferences`: add required `timezone` (text), make `notificationTime` nullable.
- **Service (`packages/api/src/services/dailyReports.ts`):** computes the user's
  timezone-aware window boundaries, gathers closed entries (all, for stats) and
  closed+commented entries (for the narrative), computes `historicRatio`/`weekRatio`/
  `openCount` deterministically (mirroring `computeDecision` in
  `services/tradeEntries.ts:5-29`), and — only if commented entries exist — calls
  `generateObject({ model: openai("gpt-5.4-mini"), schema: <zod schema for
  improvements/strengths> })`, adapting the `generateObject`+Zod+`gpt-5.4-mini` call shape
  from the unmerged `development` worktree's `services/voice.ts`.
- **Route (`packages/api/src/routes/dailyReports.ts`):** `GET /reports` (list dates that
  qualify per Decision 16), `GET /reports/:date` (lazy get-or-generate for that date,
  persisting on first generation).
- **Mobile:** new query hooks mirroring `use-stats.ts`; list + detail screens under
  `apps/mobile/src/app/(tabs)/sessions/`; an entry point added to `sessions/index.tsx`;
  device-timezone auto-upsert wired into the app-launch flow (extends the existing
  `userPreferences` hook/service from the post-session-review-notification feature).
